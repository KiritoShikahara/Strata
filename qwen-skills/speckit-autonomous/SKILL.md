# Spec Kit Autonomous Execution (自律着手)

GitHub Spec Kit: https://github.com/github/spec-kit

## Overview

「自律着手」は、要件定義（spec.md）→計画（plan.md）→タスク分解（tasks.md）→実装→検証→完了報告までを、途中で人間に質問・確認せずに一気通貫で進めるモード。[[speckit-require]] の決定フロー・生成ロジックをそのまま再利用し、その先の「実装〜完了報告」を無人化する。

対象は常に1つのSPECに確定してから作業する（新規 or 既存追記の判断は `speckit-require` と同じ）。

## 対象specの決定

`speckit-require/SKILL.md` の「決定フロー: 新規作成 or 既存追記」をそのまま使う:

- ユーザー入力にSPEC-ID・spec.mdパス・「追記/既存」指示があれば即決する。
- 迷う場合は `rg -n "# 機能仕様:" specs/SPEC-*/spec.md` とキーワードで既存SPECを検索する。
- 一致1件なら追記、複数一致は候補を提示して選択を求める（このタイミングのみ人間確認が必要。あいまいなSPEC特定は「仕様の中身」の話ではなく「どのSPECを触るか」という前提確認のため、自律着手の対象外とする）。
- 一致なしなら新規作成する。

## Phase A: spec/plan/tasks が既に揃っている場合

そのまま「Phase C: 実装フェーズ」に進む。

## Phase B: spec/plan/tasks が未作成・不完全な場合（自律生成）

`speckit-require` と同じワークフローを実行するが、**clarifyで人間に質問しない**:

1. **specify**: `.specify/templates/commands/specify.md` の手順でspec.mdを生成する。新規作成時はスクリプト出力の `WORKTREE_PATH` に移動して以降作業する。
2. **clarify（自律版）**: `.specify/templates/commands/clarify.md` の観点で曖昧点を洗い出すが、`AskUserQuestion` は使わない。曖昧点ごとに最も妥当・安全な既定値を自分で決め、spec.mdのClarificationsセクションに以下の形式で明記する:
   - 質問内容 / 採用した既定値 / 採用理由（何を優先したか）
   - 見出しは「自律着手による前提」など、通常のclarify回答と区別できるようにする。
3. **plan**: `.specify/templates/commands/plan.md` に従い、`.specify/memory/constitution.md` のゲート評価を満たしてplan.md等を生成する。
4. **tasks**: `.specify/templates/commands/tasks.md` に従いtasks.mdを生成する。TDD/テスト要求がある場合はテストタスクを必ず含める。

`specs/specs.md` の優先度・状態も忘れず更新する。

## Phase C: 実装フェーズ（tasks.mdの消化）

- tasks.mdのタスクを依存関係・並列可否の指定どおりに実装する。
- TDD要求がある場合は失敗するテストを先に書いてから実装する（[[agent-team]] の `tdd-guide` の要領）。
- 各タスクは「テスト/ビルドを実際に走らせて検証してから完了扱いにする」を徹底し、tasks.mdのチェックボックスを更新する。
- 複雑な実装や検証には `agent-team` の `code-architect` / `code-reviewer` / `build-error-resolver` / 各言語reviewer等のサブエージェントを、人間の承認を挟まず自分の判断で活用してよい。
- 実装中に発生した設計判断（ライブラリ選定、命名、細部仕様の解釈など）も、仕様の記述範囲内であれば人間に確認せず自分で決め、後述の完了報告に記録する。

## 質問しない範囲の明確化（重要な境界線）

自律着手モードが省略するのは**要件・仕様確認のための質問**であり、**安全確認**ではない。以下は自律着手モードでも通常どおり扱う（省略しない）:

- 破壊的操作・不可逆操作（force push、`git reset --hard`、ブランチ削除、履歴書き換え等）
- 共有システムに影響する操作・外部への公開行為（push、PR/Issue作成やコメント、外部サービスへの投稿、メッセージ送信等）
- ブランチの作成・切替（`speckit-require`/`speckit-update` と同様に禁止。Spec Kitスクリプトが作るworktreeのみ使用する）

これらが必要になった場合は、通常どおりユーザーに確認する。自律着手はこの確認までは飛ばさない。

## 真にブロックされた場合の例外処理

以下のように**自律的な既定値では安全に解決できない**場合のみ、そのタスクをブロック扱いにする:

- 人間しか持たない認証情報・外部アカウントの判断が必須
- 上記「省略しない」範囲に該当する操作が必要
- 仕様内に解決不能な矛盾があり、どの解釈を選んでも既存要件と衝突する

この場合でも全体を止めない。該当タスクと、それに依存する後続タスクのみをスキップし、他の実行可能なタスクは続行する。ブロック内容は完了報告でまとめて提示する。

## 完了報告（必須・日本語）

実行の最後に必ず以下を含めて報告する（対話中に確認は挟まない）:

1. 対象SPEC-IDとタイトル、spec.md/plan.md/tasks.mdのパス
2. 自律的に決定した前提・仕様判断の一覧（Phase Bの「自律着手による前提」、および実装中の設計判断）
3. 完了したタスク一覧、スキップ/ブロックされたタスクとその理由
4. テスト・ビルドの実行結果
5. 変更ファイルの一覧（`git status`/`git diff --stat` 要約）
6. 人間のフォローアップが必要なブロッカー（あれば）

## Guardrails

- ブランチ作成/切替は行わない（ユーザー管理）。
- SPEC ID形式は必ず `SPEC-[UUID8桁]` を維持する。
- すべて日本語で記述・報告する。
- 要件確認の質問はしないが、破壊的/不可逆/対外的な操作の確認は省略しない。
