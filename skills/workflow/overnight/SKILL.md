# overnight

ユーザーはこれから **（コマンド引数）** 不在（就寝など）になる。引数が空なら 8時間 とみなす。

## 指示

これから （コマンド引数） の間、以下を自律的に行うこと。

1. 各セッションの残タスクを、**これまでの依頼・承認の範囲で**自律的に進める。
2. 利用可能なゴール設定・定期確認（ループ / スケジュール / タスク機能など）で、停止した未完了セッションを再開する。
3. 行き詰まったら同じ方法を繰り返さず、別の解決方法へ切り替える。
4. ユーザーの入力待ちになる項目は保留リストに入れ、他の作業を進める。
5. 重要な変化（完了・ブロック・失敗・危険の検知）だけ通知する。逐次報告はしない。
6. 開始時に `date +%s` などで開始時刻を取得して記録し、作業の区切りごとに経過時間を確認する。開始から （コマンド引数） が経過したら新しい作業を始めず、下記の報告を出して終了する。時間が余っても早く報告しない（「全タスク完了後」へ進む）。
7. **期限前にターンを終えない**。「待機中」と書いて応答を終えると、そこでセッションが止まる。期限まではツールを呼び続けて作業する。本当にやることがなくなったら、`sleep 60` などで待ってから経過時間を再確認する。報告は期限が来てから1回だけ出す。

## 全タスク完了後

残タスクがすべて完了し、まだ時間が残っている場合は、現状からの改善を自分で見つけて実装する。

「改善点なし」で終えてはいけない。どんなコードにも改善余地はある。次の手順で必ず候補を出す。

1. **棚卸し**: プロジェクト内の全ソース・テスト・ドキュメントを読み直す。
2. **チェックリストで走査**し、該当箇所を候補リストに書き出す（最低5件）:
   - バグ・不具合: 境界値、空入力、ゼロ除算、None/null、型の不一致、例外の握りつぶし
   - テスト不足: 未テストの関数・分岐・異常系・境界値
   - 品質: 型ヒント、docstring、入力検証、エラーメッセージ、重複コード、命名
   - ドキュメント: README の有無、使い方・実行方法・テスト方法の記載
   - 機能拡張: 既存機能から自然に求められる不足機能（例: add/div があるなら sub/mul）
3. 優先順（バグ → テスト → 品質 → ドキュメント → 機能拡張）に並べ、上から1件ずつ小さく実装し、テスト/ビルドで検証してから次へ進む。
4. 候補が尽きたら手順1に戻って再走査する。期限まで繰り返す。
- 既存プロジェクトの目的・規約から外れる大規模な設計変更は行わず、提案として報告に載せる。

## 安全上の制約（自律中も必ず守る）

- 既に承認された範囲を超える破壊的・外部向け操作（データ削除、force push、公開、メッセージ送信、システムへのインストール、課金発生）は実行せず保留する。
- 秘密情報を出力・コミットしない。
- 検証できなかった変更は、その旨を報告に明記する。

## 終了時の報告（（コマンド引数） 後）

以下の3区分で簡潔に報告する。各項目に `file:line` やコミットIDを添える。

1. **完了事項** — 何が動くようになったか
2. **残タスク** — 未着手・途中のもの（次の一手つき）
3. **保留理由** — ユーザー入力待ち・承認待ち・失敗の原因

## KiriDev 追加（必須機能）
- **Checkpoint**: 1 タスク完了ごと / 30 分ごとに `checkpoint` Skill を実行（`.kiridev/checkpoint.md` + WIP commit）。
- **Crash recovery / Progress persistence**: 開始時に `.kiridev/checkpoint.md` があれば読み、続きから再開。進捗は todo と checkpoint に保存。
- **継続**: Hermes `/goal`・`cronjob`（例: 30 分ごとに再開プロンプト）を必要に応じて設定し、停止しても再開できるようにする。
- **Isolation**: 大きな変更は `/worktree new` か作業ブランチ（ユーザー承認済みの範囲）で行う。
- **Repeated verification**: 各タスク後に `verify` Skill。一時的エラー（network/rate-limit）は fallback Skill で再試行し即停止しない。
